# Как работает бот

Этот файл — о том, что происходит в диалоге и почему, шаг за шагом. Про стек,
установку и деплой см. [README.md](README.md).

Бот проводит тренировочное техническое собеседование для студента курса по системному
анализу. Всё собеседование — это конечный автомат (FSM) с пятью фазами. Состояние
всегда лежит в таблице sessions в Postgres, а не в памяти процесса: каждое входящее
сообщение бот заново читает статус сессии из БД и решает, что делать. Это значит, что
бот можно перезапускать в любой момент без потери прогресса студента.

## Кто может писать боту

Доступ по одноразовому коду вида SA2026-XXXX. Коды генерирует преподаватель заранее
через go run ./cmd/generate-codes -n 20 и раздаёт студентам. Без кода зарегистрироваться
нельзя — бот проверяет код в базе (`access_codes`) и помечает его использованным сразу
после первой успешной регистрации.

## Путь студента целиком

### 1. /start SA2026-XXXX

- Код не существует или уже использован → бот вежливо просит проверить код и попробовать
  ещё раз, ничего не создаёт.
- Код валиден и студент новый → создаётся запись в students, стартует `sessions`-запись
  в статусе INSTRUCTION, бот сразу же зовёт модель за приветственным сообщением (Фаза 0)
  и переводит сессию в QUALIFICATION.
- Студент уже зарегистрирован и /start вызван повторно без активной сессии → сразу
  стартует новая сессия (как выше), код на этот раз не нужен.
- Студент уже зарегистрирован и у него есть активная сессия → бот не трогает её молча,
  а спрашивает кнопками: "Начать заново" или "Продолжить" (см. ниже).

### 2. Фаза 0 — инструкция

Одно сообщение, ровно один раз за сессию. Бот коротко объясняет формат: сначала
несколько вопросов про уровень и цель, потом гипотезы о слабых местах, потом цикл
вопросов из банка с разбором, на каждом шаге студент сам выбирает, куда копать дальше.
Без вступлений в духе "рад помочь" — тон бота задаёт персонаж Катя Желатинка (см.
`prompts/system_prompt.md`).

### 3. Фаза 1 — квалификация

Бот по одному вопросу выясняет четыре вещи:

1. Текущий грейд (джун / мидл / сеньор)
2. Целевой грейд, на который претендует
3. Запрос — зачем пришёл именно сейчас, что хочет от тренировки
4. Самооценка — какие зоны сильные, какие западают (ориентир: архитектура, БД,
   требования, безопасность, интеграции)

Направление/индустрию бот не спрашивает — все студенты курса уже системные
аналитики, это было бы лишним вопросом.

Фаза заканчивается, как только все четыре пункта известны — не после фиксированного
числа сообщений. На каждом шаге бот получает список того, что уже выяснено, и
спрашивает только про недостающее, не переспрашивая. Если модель за 6 сообщений так и
не смогла закрыть какой-то пункт — код сам обрывает фазу и идёт дальше с тем, что есть
(аварийный потолок, чтобы студент не завис в бесконечных вопросах).

### 4. Фаза 2 — мини-аудит

Бот формулирует 2-4 гипотезы о вероятных слабых местах — явно как гипотезу
("вероятно, слабое место: X, проверим на практике"), а не как готовый диагноз. Показывает
их в рамке:


▸ МИНИ-АУДИТ
...список гипотез...


Параллельно бот отмечает 1-3 темы из фиксированного списка (интеграции, архитектура, бд,
требования, безопасность, подача) как приоритетные для будущих вопросов — это не
показывается студенту, а сохраняется в сессию и используется в следующей фазе.

### 5. Фаза 3 — цикл вопросов

Повторяется до `SESSION_CYCLE_LIMIT` раз (по умолчанию 8, задаётся переменной
окружения). Каждый цикл — это два хода:

1. Бот присылает вопрос. Вопрос берётся из банка question_bank по грейду студента.
   Если в мини-аудите нашлась тема с явной привязкой к теме вопроса — она в приоритете,
   иначе используются темы из мини-аудита, иначе любой вопрос подходящего грейда. На
   этом шаге модель не вызывается вообще — вопрос отправляется как есть из базы.
2. Студент отвечает, бот оценивает. Ответ сравнивается с тремя эталонными ответами
   вопроса (уровень джун / мидл / сеньор), бот определяет ближайший уровень и даёт
   конкретную обратную связь в рамке:
▸ ТВОЙ УРОВЕНЬ ПО ЭТОМУ ВОПРОСУ: мидл
   ...что сильно, что слабо...
   

   Сразу за рамкой — один уточняющий вопрос (дожим слабого места) или переход к
   следующему вопросу из банка.

После оценки бот сразу же, без ожидания ещё одного сообщения от студента, либо
присылает следующий вопрос, либо (если лимит циклов достигнут) переходит к финалу —
то есть студент может получить в одном ответе бота сразу оценку и следующий вопрос,
либо оценку и итоговый отчёт.

### 6. Фаза 4 — финал

Итоговый отчёт: обновлённая карта слабых зон, распределение ответов по уровням
(сколько было на джуна, сколько на мидла, сколько на сеньора), 2-3 рекомендации, что
подтянуть перед реальным собеседованием. Отчёт сохраняется в session_summaries,
сессия закрывается статусом COMPLETED.

## Диаграмма состояний


stateDiagram-v2
    [*] --> INSTRUCTION: /start CODE
    INSTRUCTION --> QUALIFICATION: приветствие отправлено
    QUALIFICATION --> QUALIFICATION: не все 4 поля известны
    QUALIFICATION --> AUDIT: все 4 поля известны или лимит 6 сообщений
    AUDIT --> QUESTION_CYCLE: рамка мини-аудита показана
    QUESTION_CYCLE --> QUESTION_CYCLE: вопрос отправлен, лимит не достигнут
    QUESTION_CYCLE --> SUMMARY: лимит циклов достигнут
    SUMMARY --> COMPLETED: итоговый отчет сохранен
    QUALIFICATION --> ABANDONED: Начать заново
    AUDIT --> ABANDONED: Начать заново
    QUESTION_CYCLE --> ABANDONED: Начать заново
    ABANDONED --> [*]
    COMPLETED --> [*]


## "Начать заново" и "Продолжить"

Если у студента уже есть активная (незавершённая) сессия и он снова пишет /start,
бот не выбирает за него — показывает две кнопки:

- Начать заново — старая сессия закрывается статусом ABANDONED, создаётся
  полностью новая сессия с нуля: обнуляются грейды, запрос, самооценка, темы из
  мини-аудита, текущий вопрос, счётчик циклов — буквально всё. Старые данные не
  протекают в новую попытку.
- Продолжить — бот проверяет, что сессия и правда ещё активна, и подтверждает.
  Дальше всё работает как обычно: следующее сообщение студента бот обработает по
  текущей фазе, которую заново прочитает из базы.

## Как бот выбирает и оценивает вопросы

- Банк вопросов (`question_bank`) наполняется отдельно, вне диалога с ботом, через
  go run ./cmd/import-questions из CSV-файла. У каждого вопроса есть грейд, тема,
  два уточняющих follow-up и три эталонных ответа (джун / мидл / сеньор) с обоснованием.
- Вопрос всегда подбирается кодом (SQL-запрос), а не моделью — модель получает уже
  выбранный вопрос в контексте и решает только, как его подать и как оценить ответ.
- Модель никогда не видит всю историю переписки — только профиль студента, карту
  слабых зон, сам вопрос с эталонами и последний ответ студента. Это осознанное
  ограничение: за счёт компактного контекста системный промпт (он большой и подробный)
  остаётся неизменным между вызовами внутри сессии, и OpenAI кэширует его — часть
  токенов на каждый вызов не тарифицируется заново.

## Что видит преподаватель

Команда /report (только для telegram_id из `ADMIN_IDS`) выгружает по каждому
зарегистрированному студенту: telegram_id, имя, число завершённых сессий, дату
последней сессии и текущую карту слабых зон. Если студентов немного — ответ придёт
текстом в чат, если больше 15 — CSV-файлом. Для всех остальных пользователей
команда /report выглядит так, будто её не существует: без кода бот не отвечает
вообще ничего.

## Устойчивость

Любое сообщение и любой колбэк (в том числе кнопки "Начать заново"/"Продолжить")
обёрнуты в middleware, которое ловит панику, логирует полный текст ошибки, стек
вызовов, telegram_id и текущий шаг FSM — и только после этого отвечает студенту
нейтральным "Что-то сломалось на моей стороне". Раньше паника в библиотеке telegram-бота
без recover тихо убивала весь процесс; теперь бот переживает падение одного диалога,
не затрагивая остальных студентов.
