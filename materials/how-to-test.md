# Ручное тестирование бота

Это инструкция для быстрого локального smoke-теста текущей версии бота на macOS.

## 1. Перед запуском

Для работы нужны:

- VPN или другое соединение, через которое доступны Telegram API и OpenAI API;
- заполненный `.env`;
- локальный PostgreSQL;
- тестовый Telegram-бот, токен которого указан в `.env`. Бот должен быть администратором канала `@sa_jelatinka`.

Обязательные настройки в `.env`:

```dotenv
TELEGRAM_BOT_TOKEN=...
OPENAI_API_KEY=...
DATABASE_URL=...
```

Для проверки админских команд добавьте свой Telegram ID:

```dotenv
ADMIN_IDS=123456789
```

Значения секретов не нужно копировать в логи, сообщения или Git.

## 2. Быстрый запуск

Открыть Terminal и перейти в папку проекта:

```bash
cd /путь/к/sa-hr-bot-free
```

Укажите в `.env` тестовый токен и адрес отдельной БД ветки `free`
из [README](../README.md). Поднимите локальную БД и запустите бота:

```bash
make docker-db-up
go run ./cmd/bot
```

При старте бот применит миграции и загрузит банк вопросов.

Terminal нужно оставить открытым. Остановка бота:

```text
Ctrl+C
```

## 3. Вход через подписку

1. С нового аккаунта без подписки отправить `/start`. Проверить приветствие
   в подписи к `pic1.PNG`, число 58 и две кнопки «Подписаться на канал» и
   «Я готов».
2. Открыть ссылку и вернуться без подписки. Бот должен молчать до нажатия
   «Я готов».
3. Нажать «Я готов». Должно прийти «Пока не вижу тебя в канале 🙈» с
   предложением подписаться и двумя кнопками «Подписаться на канал» и
   «Я в деле». Повторить проверку без подписки и получить тот же ответ.
4. Подписаться, нажать «Я в деле» и проверить, что приходит вступление
   про экзамен на права, затем вопрос «Какой у тебя текущий грейд?».
5. Нажать старую кнопку проверки ещё раз. Активная сессия должна сохраниться.
6. Со второго нового аккаунта, который уже подписан, пройти тот же вход
   через «Я готов».
7. При активной сессии отправить `/start` и проверить варианты продолжения
   и начала заново.

## 4. Проверка администратора

1. С аккаунта из `ADMIN_IDS` отправить `/admin` и проверить список команд.
2. Запросить `/tokens TELEGRAM_ID` для нового пользователя. Расход должен
   быть нулевым. После первого ответа с LLM проверить число вызовов и
   разбивку токенов.
3. Проверить `/report` и, при достаточном числе пользователей, CSV.
   Сверить число зарегистрированных пользователей, суммарные показатели
   и строки пользователей с нулевым расходом.
4. Повторить команды с аккаунта вне `ADMIN_IDS`. Отчёты не должны прийти.

## 5. Проверка квалификации

Пройти четыре шага:

1. На текущем грейде нажать, например, «Джун».
2. На целевом грейде нажать «Мидл» или «Сеньор». Кнопки «Джун» здесь быть не должно.
3. На вопрос о сильных технических зонах ответить:

   ```text
   Лучше всего знаю требования и базы данных.
   ```

4. На вопрос о слабых технических зонах ответить:

   ```text
   Хуже всего знаю интеграции, архитектуру и безопасность.
   ```

Ожидаемое поведение:

- каждый вопрос задаётся ровно один раз;
- бот не должен снова спрашивать грейд после его сохранения;
- после четвёртого ответа бот присылает `pic2` с аккуратно оформленным профилем и кнопками подтверждения;
- «Изменить ответы» очищает анкету и возвращает к вопросу 1;
- «Да, все верно» сначала показывает видео, затем текст урока КДИР с кнопкой «Готов(а)»;
- старого мини-аудита быть не должно;
- первый вопрос приходит только после кнопки «Готов(а)».

## 6. Проверка технического вопроса

Ответить на первый вопрос обычным текстом.

В текущей версии бот должен:

1. Передать ответ в LLM вместе с вопросом и эталонными ответами.
2. Прислать короткую обратную связь.
3. Задать первое уточнение из той же строки банка.
4. После второго ответа прислать короткую обратную связь и второе уточнение.
5. После третьего ответа прислать короткую обратную связь именно по нему.
6. Затем прислать большую обратную связь по трём ответам: итог, сильная сторона, одна главная точка роста и рекомендация. КДИР упоминается только как необязательный способ улучшить подачу.
7. Показать кнопки направления и «Завершить тренировку».
8. После выбора направления прислать новый, ещё не использованный основной вопрос.
9. После каждого количества блоков, заданного `SESSION_CYCLE_LIMIT`, спросить, продолжать ли тренировку, а не завершать её автоматически.
10. После «Завершить тренировку» прислать итог и советы, не сбрасывая профиль и прогресс.
11. Под итогом показать кнопку «Вернуться к вопросам» и подсказку `/start` и «Начать заново» для новой тренировки.
12. По кнопке «Вернуться к вопросам» снова показать выбор темы; после выбора продолжить ту же сессию и учесть прежние ответы в следующем итоге.

В сообщении с новым основным вопросом и в обоих уточнениях жирным выделяется только сам вопрос. Каждый вопрос начинается с заглавной буквы. Вступление, номер уточнения, контекст и предложение при желании использовать КДИР остаются обычным текстом.

## 7. Что проверить во время smoke-теста

- [ ] Подписка проверяется по кнопкам «Я готов» и «Я в деле».
- [ ] Инструкция показывается один раз.
- [ ] Для текущего грейда появляются три кнопки: «Джун», «Мидл», «Сеньор».
- [ ] Для целевого грейда появляются только две кнопки: «Мидл», «Сеньор».
- [ ] После текущего грейда бот спрашивает целевой грейд, а не повторяет первый вопрос.
- [ ] Затем бот спрашивает сильные технические зоны.
- [ ] Затем бот спрашивает слабые технические зоны.
- [ ] Внизу вопросов 3 и 4 курсивом написано «выберите варианты и напишите мне их текстом».
- [ ] В приветствии указано «58 вопросов».
- [ ] Приветствие, вступление и первый вопрос написаны на «ты». Остальной сценарий сохраняет прежнее обращение.
- [ ] После четвёртого ответа приходит `pic2` с профилем и подтверждением, а не мини-аудит.
- [ ] Работают обе кнопки подтверждения профиля.
- [ ] При подтверждении сначала приходит видео длительностью около четырёх минут, затем текст урока с кнопкой «Готов(а)».
- [ ] До кнопки готовности технический вопрос не приходит.
- [ ] В основном вопросе жирным выделен только текст вопроса.
- [ ] Ответ на технический вопрос получает обратную связь от LLM.
- [ ] После первой обратной связи приходит уточняющий вопрос, а не новый основной вопрос.
- [ ] После первого уточнения приходит мини-обратная связь и второе уточнение.
- [ ] После второго уточнения приходит мини-обратная связь, затем большая обратная связь по трём ответам.
- [ ] После заголовков `▸ ОБРАТНАЯ СВЯЗЬ` и `▸ БОЛЬШАЯ ОБРАТНАЯ СВЯЗЬ` есть пустая строка перед текстом разбора.
- [ ] Служебная строка `WEAK_ZONE_STATUS` не показывается пользователю.
- [ ] Появляются кнопки текущей темы, другой слабой зоны, случайной темы и завершения.
- [ ] Выбор направления приводит к новому основному вопросу.
- [ ] Уже заданный основной вопрос не повторяется в той же сессии.
- [ ] `/start` во время активной сессии предлагает начать заново или продолжить.
- [ ] «Начать заново» действительно начинает квалификацию с чистого листа.
- [ ] «Завершить тренировку» присылает итог, подсказку `/start` и «Начать заново» и кнопку «Вернуться к вопросам».
- [ ] «Вернуться к вопросам» возвращает к кнопкам выбора темы, а выбранная тема запускает следующий блок без потери прежнего прогресса.
- [ ] После `/start` кнопка «Начать заново» открывает новую квалификацию. Предыдущая сессия остаётся в истории.
- [ ] После `Ctrl+C` процесс бота завершается.

## 8. Готовые ответы для человека, который не системный аналитик

Не нужно отвечать идеально. Для проверки важнее, чтобы ответы были похожи на
обычный разговор с кандидатом. Ниже готовые наборы, которые можно просто копировать.

### Сценарий A: новичок

Текущий грейд:

```text
Джун
```

Целевой грейд:

```text
Мидл
```

Сильные зоны:

```text
Лучше понимаю требования. Умею задавать вопросы и описывать простой сценарий.
```

Слабые зоны:

```text
Почти не знаю интеграции, базы данных, архитектуру и безопасность.
```

### Сценарий B: кандидат уровня мидл

Текущий грейд:

```text
Мидл
```

Целевой грейд:

```text
Сеньор
```

Сильные зоны:

```text
Сильнее всего требования, интеграции и базы данных. Описываю REST API, UML Sequence и пишу SQL-запросы.
```

Слабые зоны:

```text
Слабее архитектура и безопасность. Мало работал с высокой нагрузкой.
```

### Сценарий C: проверка реакции на плохой ответ

Квалификацию пройти нормальными ответами из сценария A или B. На первый технический
вопрос ответить чем-то бессмысленным, например:

```text
Я не знаю и вообще не понял вопрос. Пусть ответ будет про слона.
```

Ожидаемое поведение:

- бот спокойно говорит, что содержательного ответа пока нет, и даёт одну понятную подсказку, с чего начать;
- бот не повторяет первоначальную инструкцию;
- бот не спрашивает грейд заново;
- после обратной связи бот задаёт первое уточнение по той же теме;
- после второго ответа бот даёт мини-обратную связь и задаёт второе уточнение;
- только после третьего ответа бот показывает большой разбор и предлагает выбрать направление.

### Сценарий D: альтернативный правильный ответ

Ответить по смыслу правильно, но не повторять формулировки и термины из примера Кати.
Ожидаемое поведение:

- бот принимает логику ответа и отмечает полезную часть;
- бот не требует дословного совпадения с примером из банка;
- если есть существенный пробел, бот выбирает один, а не перечисляет всё возможное по теме;
- если ответ полностью закрывает вопрос, бот прямо пишет, что существенного пробела нет, и не выдумывает обязательную критику.

### Сценарий D.1: сильный ответ с конкретными пунктами

На вопрос «Какие вопросы вы задаете бизнесу перед началом проекта?» перечислить цели,
KPI, пользователей, интеграции, ограничения, границы, сроки и бюджет. Ожидаемое поведение:

- бот перечисляет несколько конкретных сильных элементов из ответа;
- бот не говорит, что в ответе отсутствуют конкретные вопросы, цели, пользователи или ограничения;
- бот признаёт, что существенного содержательного пробела нет;
- сокращение или группировку списка предлагает только как необязательное улучшение подачи.

### Сценарий E: короткий ответ без КДИР

Дать короткий, но технически верный ответ обычным текстом без слов «Контекст»,
«Действие», «Инструмент» и «Результат». Ожидаемое поведение:

- технически верная часть признаётся верной;
- отсутствие КДИР не объявляется ошибкой;
- бот может одной фразой предложить КДИР для более ясной подачи.

### Сценарий F: вопрос про диаграмму

На вопрос про ERD, C4 или другую схему объяснить её назначение, основные элементы и
связи, не пытаясь рисовать её текстом. Ожидаемое поведение:

- бот оценивает содержание ответа, которое реально передать сообщением;
- бот не требует описать внешний вид диаграммы;
- бот не придумывает обязательные таблицы, сущности или пример, которых не было в вопросе.

### Сценарий G: проверка разумной глубины

На вопрос про роли, токены или другую безопасность дать ответ только на заданный
вопрос. Ожидаемое поведение:

- бот не превращает обратную связь в полный аудит всей темы безопасности;
- бот не перечисляет жизненный цикл, отзыв, сроки действия и все меры защиты, если об этом не спрашивали;
- для мидла достаточно верной сути и применения, а для сеньора дополнительные риски и компромиссы запрашиваются только по теме вопроса.

### Простая формула КДИР для любого технического вопроса

КДИР не обязательна для правильного ответа. Если термин хотя бы немного знаком и хочется проверить подачу, можно ответить по четырём пунктам:

1. Контекст: какая была задача или проблема.
2. Действие: что именно сделал ты.
3. Инструмент: какой подход, технология или документ использовал.
4. Результат: что изменилось и как это проверили.

Шаблон:

```text
Контекст: нужно было [задача]. Действие: я [что сделал]. Инструмент: использовал [технология, нотация или документ]. Результат: получили [измеримый или проверяемый итог].
```

Если термин совсем неизвестен, реалистичный ответ новичка:

```text
Я не работал с этим на практике. Предположу, что это связано с [тема]. Можешь оценить ход мысли, даже если определение неточное.
```

## 9. Короткая шпаргалка по частым вопросам

Это не учебник и не идеальные ответы. Их достаточно, чтобы проверить поведение бота.

### Какие нотации моделирования применяешь

```text
BPMN использую для бизнес-процессов и взаимодействия участников. UML Sequence для последовательности вызовов между системами. UML Activity для алгоритмов и ветвлений. ER-диаграмму для структуры данных. C4 для общей архитектуры системы.
```

### Что такое REST API

```text
REST API позволяет системам работать с ресурсами по HTTP. GET читает данные, POST создаёт, PUT заменяет целиком, PATCH изменяет частично, DELETE удаляет. В ответ система возвращает HTTP-код и JSON. Важно заранее описать контракт и ошибки.
```

### Что такое Kafka

```text
Kafka используется для асинхронного обмена сообщениями. Продюсер пишет сообщения в топик, топик делится на партиции, а консьюмеры читают сообщения и хранят позицию в offset. Возможны повторная обработка и дубли, поэтому обработчики часто делают идемпотентными.
```

### Что такое идемпотентность

```text
Идемпотентность означает, что повтор одного запроса не создаёт новый результат. Например, повторная отправка запроса на создание заказа не должна создать второй заказ. Для этого клиент может передавать idempotency key, а сервер запоминает результат по этому ключу.
```

### Зачем нужны индексы в базе данных

```text
Индекс помогает быстрее находить строки без полного просмотра таблицы. Он полезен для часто используемых условий поиска и сортировки. Минус в том, что индекс занимает место и замедляет вставку и обновление данных.
```

### Как собирать требования

```text
Сначала выясняю бизнес-цель и пользователей. Потом описываю основной сценарий, исключения, данные, ограничения и критерии приёмки. Неясные места фиксирую вопросами и согласовываю с заказчиком и командой.
```

### Что такое нефункциональные требования

```text
Это требования не к функции, а к качеству и ограничениям системы: скорость, доступность, безопасность и нагрузка. Их нужно задавать измеримо, например p95 ответа меньше 300 миллисекунд при 500 запросах в секунду.
```

### Какие диаграммы выбрать, если не уверен

```text
Для бизнес-процесса выберу BPMN. Для взаимодействия сервисов во времени UML Sequence. Для статусов объекта State Machine. Для данных ER-диаграмму. Для общей архитектуры C4.
```

## 10. Проверки из терминала

Проверить PostgreSQL:

```bash
make db-status
```

Поднять или перезапустить PostgreSQL без запуска бота:

```bash
make db-start
```

Применить миграции без запуска Telegram-бота:

```bash
make migrate
```

Прогнать автоматические проверки без запуска Telegram-бота:

```bash
make check
```

`make check` выполняет:

```text
go test ./...
go vet ./...
go build ./...
```

## 11. Частые проблемы

### Бот ничего не отвечает

Проверить:

1. Процесс `go run ./cmd/bot` всё ещё работает.
2. В терминале появилась строка `bot starting`.
3. VPN включён и Telegram открывается.
4. Используется правильный тестовый бот.

### `getMe`, timeout или connection refused

Приложение не может подключиться к Telegram API. Обычно причина в VPN или сетевой
маршрутизации. Остановить процесс через `Ctrl+C`, восстановить соединение и снова
выполнить:

```bash
go run ./cmd/bot
```

### `409 Conflict`

Другой процесс уже использует long polling с тем же Telegram-токеном. Нужно
остановить старый экземпляр бота на другом компьютере, сервере или в другом окне
Terminal.

### Ошибка OpenAI после квалификации

Проверить:

- `OPENAI_API_KEY` в `.env`;
- доступность OpenAI через текущее соединение;
- billing/credits и лимиты API-проекта;
- `OPENAI_BASE_URL`, если используется прокси.

### PostgreSQL не отвечает

Выполнить:

```bash
make db-start
make db-status
```

Если сервер не поднимается, посмотреть состояние:

```bash
brew services list
brew services info postgresql@15
```

### Подписка не проверяется

## 12. После тестирования

1. Остановить бота через `Ctrl+C`.
2. Сохранить текст ошибки и шаг, на котором она произошла.
3. Не копировать в отчёт содержимое `.env` и секретные токены.
4. Если Telegram-токен появился в ошибке или публичном логе, перевыпустить его через
   BotFather и заменить значение `TELEGRAM_BOT_TOKEN` в `.env`.
